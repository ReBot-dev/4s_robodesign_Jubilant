# OCR 比較結果（2026-10-19〜20）

テスト文書 5 種類（お知らせ・請求書・時間割・チラシ・仕様書）を印刷してスマホで撮影し、
同じ画像を OSS の OCR 5 種類と Claude 4 モデル、Gemini 2 モデル（英語版のみ）に読ませて、正解テキストで採点した。
本番で読むのは海外の文書なので **英語版が本命**。日本語版は先に行った予備の比較。
方法の詳細は [`README.md`](README.md)、1 枚ごとの点数は `en/results/scores.csv`（英語）と `results/scores.csv`（日本語）。

## 結論

1. **Claude（4 モデルとも）は英語でもほぼ完璧。** 正対補正後なら Haiku・Opus は文字誤り率 0.0%。残った誤りは「左右に並んだ欄を読む順番」だけで、文字の読み間違いはほぼ無い。Haiku は最も速く（1 枚約 6 秒）、精度も最上位。
2. **Gemini も精度は十分。無料枠で実用になるのは Flash-Lite。** Gemini 3.8 Flash は補正後で文字誤り率 0.1% と Claude 並みだが、無料枠は 1 日 20 回までで、混雑のため 1 枚に 1〜5 分かかった。Gemini 3.5 Flash-Lite は 0.5〜0.6%・1 枚約 5 秒・無料枠 1 日 500 回で、無料の選択肢としては最有力。
3. **OSS で実用になるのは YomiToku と Surya。** 日本語特化と言われる YomiToku が英語でも OSS の最良クラス（文字誤り率 7%、数字・記号 100%、1 枚 20〜25 秒）。Surya は最も正確（1.1%）だが CPU で 1 枚 5 分かかる。
4. **ArUco での正対補正は必須。** 写真のままだと OSS はほぼ崩れる（PaddleOCR だけは向きの自動補正があり比較的もつ）。補正すれば D435i 程度の画質でも精度はほとんど落ちない。
5. **英語は日本語より読みやすい。** OSS の多くで、日本語より行の再現率・数字の正確さが上がった。

## Gemini の無料枠について（2026-10 時点）

Gemini は Google AI Studio で作った API キー（無料枠）で、画像を 1 枚ずつ API に送って読ませた（`run_gemini.py`。指示文は Claude と同じ）。

| モデル | 1 分あたり | 1 日あたり | メモ |
|---|---|---|---|
| Gemini 3.8 Flash | 5 回 | **20 回** | 混雑で 1 枚 1〜5 分。`503 UNAVAILABLE`（混雑）で断られることもある |
| Gemini 3.5 Flash-Lite | 15 回 | **500 回** | 1 枚約 5 秒。今回は一度も制限に当たらなかった |
| Pro 系（2.5 Pro・3.1 Pro） | 0 | 0 | 無料では使えない |

- 上限は「無料枠かどうか」で決まり、アカウントを替えても同じだった。「無制限」の表示は Live API（音声・映像のリアルタイム用）だけ。
- 無料枠では、送ったデータが Google のサービス改善に使われることがある。本物の書類を読ませるときは注意。
- 時間は API の応答時間そのもの。Claude は Claude Code のエージェント経由で測った目安なので、厳密な比較ではない。

## 指標の意味

| 指標 | 意味 |
|---|---|
| 行の再現率 | 正解の各行が、読み取り結果のどこかに 8 割以上の一致で見つかった割合（読む順番は問わない） |
| 完全一致行 | 正解の各行が、一字一句そのまま見つかった割合 |
| 数字・記号 | 金額・日付・型番・単位など、数字や記号を含む語がそのまま読めた割合 |
| 文字誤り率 | 全文を比べたときの誤り文字の割合。**読む順番が違うだけでも誤りになる**ので、2 段組みや左右に並ぶ欄があると大きくなる |
| 元に無い行 | 正解のどこにも似ていない行の数（でっち上げ・ゴミ。OSS では四隅のマーカーを文字と誤認した行が多い） |

## 気づいたこと

- **Claude の誤りは読む順番だけ。** 英語の請求書で、Fable は「Amount Due」の枠を、Sonnet は発行元の欄を、別の位置で読んだ。文字は合っている。
- **PaddleOCR の「行の取りこぼし」は見かけだけ。** 表のセルを列ごとに出力するため、正解の「表の 1 行」とつながらず取りこぼしに数えられる。文字自体は読めている。2 段組みのチラシでは左右の段を混ぜて読む（文字誤り率 33%）。
- **YomiToku は読み順の推定（`DocumentAnalyzer`）を使うことが必須。** 単純な `OCR` クラスだと行が逆順に出る。英語でも表をセル単位で正しく構造化できた。誤りは見出しまわりの順番と、`·`（中黒）を `-` と読む程度。
- **Claude Haiku は日本語の逆さまの写真で一度でっち上げをした。** 注記の「施錠中」を「授業中」と推測で書いた。補正後の画像や英語では起きていない。
- **EasyOCR と Tesseract は、マーカーや罫線を文字と誤認しやすい**（元に無い行が多い）。

## 採点と方法の注意

- **同じ文書を続けて読ませると Claude は前の読み取りを写す。** 最初の実行で全条件の結果が一字一句同じになったため、1 つのエージェントには同じ文書を 1 枚しか見せない形でやり直した。正解ファイルを開いていないことは実行ログで確認済み。
- **「数字・記号」の採点を途中で修正した。** 最初の版は空白を消してから語を取り出していたため、英語では単語がつながって 1 語が長くなり、点数が不当に低く出た。空白で区切ってから取り出すように直し、日本語版も付け直した（日本語版の数字・記号は OSS で数ポイント上がった）。
- OSS はすべて GPU のないノート PC（CPU のみ）で測った。GPU があれば大幅に速くなる。
- Claude の時間は「Claude Code のエージェント全体の所要時間 ÷ 枚数」で、API を直接呼ぶ場合とは違う目安。Claude Code は大きい画像を縮小して渡すため、API で解像度を指定すると結果が変わる可能性がある。

## 次にやること

- 方針の候補：
  - **精度重視・ネット接続あり** → 補正画像を Claude（Haiku で十分）に直接渡す。OCR と翻訳を 1 回で済ませることもできる
  - **無料で済ませたい** → 補正画像を Gemini 3.5 Flash-Lite に渡す（1 日 500 回まで。混雑時の代わりを用意しておく）
  - **ネットなしでも動かしたい** → 正対補正 + YomiToku（`DocumentAnalyzer`）→ 翻訳だけ Claude
- 実機の D435i で撮った画像で、同じ比較を一度回して確かめる（今回はスマホ写真を縮小して代用した）。
