# プロジェクトの文脈と進め方

更新日: 2026-10-26

このファイルは、プロジェクトの目標・現在の実装・進め方の記録です。2026-10-26にワークスペースのコードと照合しました。目標や検討案を実装済みとして扱わないでください。

## プロジェクトの核

CRANE-X7にライトを持たせて書類を追従させ、時間とともに「うとうと」し、手を振ると起きるインタラクションシステムを作る。

ELEGNT論文のキーフレーム再生ベースの表現に対し、**連続的な内部状態から表現をパラメトリックに生成する**ことを差異化の軸とする。設計の背骨は **「状態 → パラメータ → 動作」**。

これは研究上の目標。現在の実装では眠気は連続値だが、動作への反映はしきい値による開始・継続判定であり、振幅や周期を眠気に応じて連続的に変える処理はない。

かいとさんの担当はインタラクション（内部状態管理とジェスチャー認識）。

## 現在の実装

### 眠気モデルと表現

眠気モデルは次の式を用いる。

```text
dS/dt = k_up · (1 − α · m) · (1 − S) − k_down · 外部刺激
```

- `drowsiness_node.py` が `/activity`（`std_msgs/msg/Float32`）を購読し、眠気 `S` を `/drowsiness`（同型）に配信する。
- `S` は眠気、`m` は自己運動の活動度。初期値はいずれも0。
- 既定値は `k_up=0.03`、`alpha=0.8`、`k_down=0.1`、更新頻度20 Hz。経過時間を使ったオイラー積分後、`S` を0〜1に制限する。
- 自己運動は眠気の上昇を遅らせる。眠気を下げる作用はない。外部刺激による覚醒項は計算関数にあるが、ノードは `external_stimulus=0.0` を渡しており、刺激トピックを購読していない。手振りによる覚醒は未接続。
- 「30秒くらいでうとうとする」という目標に対し、`k_up=0.03`、表現開始しきい値 `S=0.6`。静止・`S=0`からの理論到達時間は約30.5秒。
- `drowsiness_expression.py` は、頭を下げるだけという旧案から変更され、**肩tilt関節を現在姿勢を中心にsin波で上下往復させる**。対象は `crane_x7_shoulder_revolute_part_tilt_joint`。既定値は振幅±5°、周期4秒で、他の6つのアーム関節は保持する。
- `S >= 0.6` で開始し、しきい値以上の間は往復を繰り返す。各往復後に0.3秒待つ。しきい値未満になった場合は、進行中の往復を終えてから次の往復を止める。眠気に比例した角度制御やヒステリシスは未実装。
- 軌道は `/crane_x7_arm_controller/follow_joint_trajectory` アクションへ送る。`/robot_description` のhardware pluginがGazebo用であることを確認するため、現在の表現ノードはGazebo専用。眠気・関節状態の鮮度や関節可動域・速度上限も確認する。

### 活動度の取得

- `activity_monitor.py` で `/joint_states` を購読する。
- **`velocity` 配列が空でなければその値を使い、空の場合のみ `position` の差分から計算する**。差分の時間にはノードの時計で測った受信時刻を使う。「常にposition差分を使う」という以前の説明は実装と異なる。
- 角速度ベクトルのノルムが `vel_threshold=0.05` rad/sを超えるかで0/1に判定し、`smoothing=0.1` のローパスで活動度を更新する。`/activity` に配信する。
- `/expression_active`（`std_msgs/msg/Bool`）がTrueの間は活動度の更新を凍結し、直前の値を配信し続ける。0へのリセットではない。角速度計算用の前回位置・時刻は引き続き更新する。
- 狙いは、表現動作自体が活動度に入り、眠気の上昇を抑えてしまうことを防ぐこと。現在は活動度によって眠気が下がることはない。
- Mock componentsが非空の `velocity` を0埋めで配信する場合、現コードはその0を採用する。この問題へのposition差分の常用は未実装。

### 起動と通信のつながり

```text
/joint_states → activity_monitor → /activity → drowsiness_node → /drowsiness
                      ↑                                             ↓
               /expression_active ← drowsiness_expression → 軌道アクション
```

- `simulation/manual_activity.launch.py` はGazebo・MoveIt・活動度・眠気・グラフ・表現ノードを起動する。表現は既定で有効で、`nod:=false` で無効化できる。各ノードはシミュレーション時刻を使用する。
- 手動launchは `ROS_DOMAIN_ID=87` を設定する。別端末でトピックを確認する場合も同じdomainに合わせる。
- `simulation/activity_check.launch.py` はheadlessのGazebo・活動度・眠気を起動する。表現ノードは自動起動しない。

## 未解決の論点

以下はまだ決定していない。確定した仕様として扱わない。

1. **表現動作に伴う視野の変化**: アーム先端カメラの視野が動作に伴って変わり、手振りが見えにくくなる可能性がある。将来、眠気に応じて深くうなだれる表現を導入する場合は、深く眠るほど見えにくくなる問題も検討する。現実装の振幅は一定。視野変化を表現として活かすか、対策するかは未決定。
2. **手振り判定の方式**: 「切り返し回数」案と、FFTで1〜4 Hz帯のパワーを見る連続値方式のどちらにするかは未決定。どちらも現在のコードには未実装。
3. **依存関係の衝突への対処**: MediaPipeとROS 2 JazzyのNumPy衝突に対し、`--system-site-packages` 付きvenvを使うか、別プロセス化するかは未決定。今回のコード照合では、インストール環境や衝突の再現までは確認していない。

## 一緒に理解しながら進めるための約束

かいとさんから「全部アトリにやってもらってる感じ」「トピックのところがふわっとしている」というフィードバックがあり、完成コードを渡す進め方から、仕組みを一緒に理解する進め方へ切り替えた。

- 完成コードを一方的に渡して先へ進めない。
- 内部状態、ROS 2のトピック、ノード間の通信がどうつながるかを、小さな確認と説明を通して一緒に理解する。
- 操作や変更の目的を説明し、かいとさんが実際の出力と仕組みを結び付けられるようにする。
- 新たに具体的な実装や作業を依頼された場合は、その依頼を尊重する。
